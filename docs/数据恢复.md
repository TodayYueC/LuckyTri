# 她的一生：备份、迁移和恢复

数据库使用 WAL、FULL 持久化和写锁等待。升级前运行 `npm run backup`；运行中仍按设定定期自动备份。完整和自动备份都先生成临时文件，经过 SQLite 完整性、引用检查后发布，并附带 `.db.json` 校验清单：SHA-256、应用版本、数据库版本、表结构签名及生活记录数量。复制备份时把两个文件一起复制到另一块磁盘。

```powershell
npm run recovery -- verify --backup "data/backups/某份备份.db"
npm run recovery -- restore --backup "data/backups/某份备份.db" --to "data/recovered-life.db"
```

恢复只发布到一个全新的文件；目标或其 WAL/SHM 文件已存在就拒绝。恢复前检查清单与完整性，恢复后再检查新文件；现有实例和现有数据库不会被覆盖。旧备份没有清单时仍可检查完整性并恢复，命令会说明它没有 SHA-256 清单。

验证恢复副本后，先停止原实例，再为所需实例设置 `DB_PATH` 指向新文件并启动。保留原数据库和原备份，直到确认恢复后的经历、自我、日记、关系和权限都符合预期。测试恢复副本时用另一端口并设置模拟模式，避免重复 QQ 实例。

数据库通过 `PRAGMA user_version` 标记结构版本。旧版已有数据首次迁移前，自动保存经过检查的 `luckytri-migration-*.db` 快照和清单；它不参与自动备份轮换。迁移成功后才记录新版本。新版本数据库被旧程序打开时只读拒绝，避免降级改坏记录。后续变更数据库结构时应递增 `DATABASE_VERSION`，保持迁移幂等，并增加旧库恢复与升级回归。

校验能发现损坏及清单不一致；SHA-256 清单不提供密码学签名。数据库备份包含已入库的知识段落、向量及阅读记录，外部图片附件与 `data/knowledge` 中的原文件需要另外复制。同一磁盘上的备份无法抵御整盘故障。
