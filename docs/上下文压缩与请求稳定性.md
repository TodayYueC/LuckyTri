# 上下文压缩与请求稳定性（2026-09-24）

本次修复依据两份生产诊断日志：一份记录最近 24 小时的 36 次模型调用失败，一份记录 11:06 前后 50 秒内约 159 万输入 token 的消耗尖峰。

## 原因

**Token 消耗**

- 会话默认 `contextMessages: 0`，语境构建把它理解为“一直装历史，直到模型输入预算用完”。GPT-6 Luna 选了 1.05M 档后，3107 条历史每次全部带上，单次请求约 26.7 万输入 token，输出却只有两三百。
- 一批消息至少跑 decision 和 generation 两次，每次都带完整历史；deepCheck 再全量复审一次，不通过还会重写并再复审。生成期间来了新消息，整轮作废重跑。
- 前缀缓存几乎没有生效。GPT-5.6 以后的模型只在消息边界精确命中缓存，而旧请求是“系统提示 + 一条每轮都在变的巨大 user 消息”，所以只命中了系统提示词（日志中 `cached_tokens=4226`，不是 128 的倍数，符合按精确边界计数）。其余 26 万 token 每次按 1.25 倍价格写入缓存，下一轮又读不到。
- 每条历史带着空字段和重复的毫秒时间，每次请求还申请 128K 输出上限。

**请求出错**

- 2–3 MB、26 万 token 的请求本身就容易超时、限流，或在上传途中被网关或代理重置，而且已经逼近 272K 的长上下文计价线。
- `opencode-zen` 请求没有带 `User-Agent` 和 `x-opencode-session`，OpenCode 用这两个头做路由和缓存。
- 模型返回 HTTP 错误时响应正文被丢弃，日志里只剩状态码；重试总共只等约 3 秒，没有熔断，也没有备用模型。
- 凌晨多个供应商同时出现 100–700ms 就失败的连接错误，更像本机网络或代理中断，代码只能缓解。
- 预设 `opencode-zen-qwen3.8-max` 不在 Zen 的模型列表里，选它必定失败。

## 修改

### 分层上下文压缩

每次请求只带“最近原文 + 分层摘要 + 长期记忆 + 本轮检索到的相关旧消息”。

- 原文从最新一段摘要之后开始，默认 40 条，可在会话设置里改为 10–500。原文超过“设定条数 + 30”时，最旧的 30 条在后台压成一段细摘要，所以原文保持在 40–69 条之间；两次压缩之间历史前缀不变。
- 摘要分四级，越久远越概括：

  | 级别 | 每段覆盖 | 字数上限 | 何时合并 |
  | --- | --- | --- | --- |
  | L0 细摘要 | 30 条 | 约 300 字 | 超过 4 段时最旧 3 段合并为 L1 |
  | L1 中摘要 | 约 90 条 | 约 450 字 | 超过 3 段时最旧 3 段合并为 L2 |
  | L2 粗摘要 | 约 270 条 | 约 600 字 | 超过 3 段时最旧 3 段并入 L3 |
  | L3 远期摘要 | 更早的全部 | 约 900 字 | 滚动更新，只保留一段 |

- 每段摘要带 `keyPoints`：没结束的事、约定和承诺、明显的情绪、关系变化，以及她自己看法和立场的变化。合并时从子摘要继承，只有明确结束或被新信息取代才删除；带密码、密钥等内容的关键点会被过滤。
- 摘要的时间段由本地消息时间计算，不让模型推断。更早的内容由已有阶段摘要、长期记忆和相关旧消息召回衔接。
- 压缩在每轮回复后后台检查一次，服务器每分钟的维护任务也会补做；每个会话同时只跑一个任务，全局最多两个，失败后按 1、5、15、30 分钟退避。压缩使用会话模型能设置的最低推理档，主模型失败时同样走备用模型。
- 已有长会话第一次压缩只回溯原文窗口之前约 120 条。回放只使用在回放批次之前结束的摘要；模拟模式只用原文。
- 清空上下文和删除会话会同时删除摘要。压缩提示词 `summary` 和 `summaryMerge` 可在人格页的指令编辑器里修改；会话设置页有“上下文压缩”开关和只读的“语境摘要”列表。

### 请求结构与缓存

- GPT 系列模型改为：developer 系统提示 → user 稳定头部（人格、会话、分层摘要）→ 每条原文一条 user 消息 → developer 本轮数据。这样每次调用都能复用上一次调用写入的前缀，本轮易变数据不再按 1.25 倍写入缓存。openai、opencode 和 openrouter 上的 GPT 请求附带 `prompt_cache_key`（会话 HMAC 加阶段）。
- 其他供应商保持单条 user 消息，稳定内容在前、易变内容在后，按前缀缓存。
- 发给模型的内容去掉空字段、内部字段和重复的毫秒时间；被引用但早于窗口的消息移到末尾的 `quoted`，不打乱前缀。
- `opencode-zen` 也发送 `User-Agent` 和 `x-opencode-session`。
- 输出上限按阶段设置：decision 和 validation 2K，vision 和 summary 3K，generation 和 rewrite 4K，memory 8K，再按推理档加余量（最高 32K），不超过档案上限；被截断时用完整上限自动重试一次。
- 各协议的 usage 统一为输入、缓存读、缓存写、输出、推理五项，调试页的处理记录显示“输入 X（缓存读 Y / 写 Z）· 输出 W”。

### 减少整轮浪费

- 复审只带本批消息、回复目标和证据、它们的引用链与最近 30 条原文，不再带摘要、召回和预算。
- 生成、复审、重写开始前先检查语境是否已经过期；过期就停下，把这批消息留给下一轮，不再发请求。
- 过期判断改为比较会话指纹（会话策略、人格、提示词、模型档案、启用状态和清空次数），其他会话或后台任务的写入不再作废正在生成的回复。

### 请求稳定性

- 网络错误能区分连接重置、代理隧道失败、TLS 错误和超时，并记录脱敏后的底层原因；HTTP 错误带上供应商给出的原因（脱敏、截断）。
- 重试改为带随机抖动的指数退避（约 0.6 秒起、单次最长 8 秒、总计不超过 45 秒），继续遵守 `Retry-After`；520–523 也会重试。每次尝试记录状态码、原因、等待时间和耗时，每次调用记录请求体字节数。
- 同一网关上的同一模型连续 3 次最终失败后暂停 30 秒，反复失败时逐步延长到 2 分钟，之后放行一次试探请求。连接测试不受熔断影响。
- 会话可设置备用模型：主模型重试后仍失败（网络、超时、429、5xx）、熔断中，或返回 401、402、403、404 时，这一步改用备用模型，并在处理记录中写明原因。JSON 格式问题仍由原有兜底处理；带图片的调用只在备用模型能看图时切换。
- `opencode-zen-qwen3.8-max` 换成 Zen 实际提供的 `qwen3.8-flash`。

### 数据清理

处理记录每小时清理一次 14 天以前的部分。上下文变小后，单条记录也从数 MB 降到约百 KB。

## 验证

- 171 项自动化测试、Vue Studio 冒烟测试通过；本次改动的文件通过格式检查。
- 本地用真实 `ModelManager` 和编排器，对一个按 GPT-5.6 缓存规则模拟的 Responses 服务跑了 300 条群聊（100 轮）：decision 和 generation 平均请求体 17–22 KB，约 7–9 千输入 token，其中约 71–75% 可从缓存读取；decision 的输出上限从 128000 降到 10240；400 条事件最终整理成 3 段中摘要和 3 段细摘要，原文保持在 40–69 条。这是按公开规则做的模拟，不代表供应商账单。
- 本地无法验证的部分：供应商实际的缓存命中和计费、Zen 是否把 `prompt_cache_key` 透传给上游，以及家里网络和代理的真实情况。上线后请在调试页查看缓存读取比例和失败记录里的具体原因。

## 合并到 love 分支

- 本次在 `main` 上实施。`love` 分支的时间系统每次独处运行结束都会执行 `store.revision++`；改用会话指纹判断过期后，它不会再作废正在生成的回复。
- 时间系统通过 `models.call` 发起的独处调用会自动用上错误诊断、重试退避和熔断。它的阶段名是 `reflection`，不在输出上限表里，合并时可以在 `STAGE_OUTPUT` 里补一项；如需备用模型，可以同样用 `withFallback` 包一层。
- 合并时 `model-manager.js`、`orchestrator.js`、`context-builder.js` 预计会有冲突，需要保留两边的改动。
